# Climbing Monkey backend implementation plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Execute each behavior through a runnable red → green → regression cycle. The user authorized implementation and subagents in this session.

**Goal:** A persistent FastAPI backend supporting the complete evidence → profile → eligible quest → monkey XP loop, plus an optional MediaPipe image-analysis boundary.

**Architecture:** A Python service in `backend/` with Pydantic request validation, SQLite persistence, bearer-token isolation, pure profile derivation and an injectable pose adapter. Clients retain their token locally; server photo processing requires explicit consent and does not retain uploaded images.

**Tech Stack:** Python 3.12–3.13 (development: 3.12), FastAPI, Pydantic 2, SQLite, pytest, HTTPX, Ruff, Pillow, optional MediaPipe Tasks and NumPy.

**Spec:** `docs/climbing-app-design.md`, `docs/climbing-monkey-alignment.md` and the user's instruction to implement a Python/FastAPI backend using TDD.

## Global constraints

- Profile first: evidence, understandable style records, one achievable next action.
- Unknown is not zero. No calibrated grade predictions, diagnosis or invented force measurements.
- Pet XP is separate from ability: 10 XP per unique completed quest, level `1 + xp // 50`.
- Current hand symptoms pause affected loading suggestions; skipping/rest never removes XP.
- Every persisted record belongs to a bearer-token identity; no cross-user reads or writes.
- Record provenance, timestamps and test setup. Uploaded images are transient and consent gated.
- Real external-provider OAuth, clinical pain routing and broad video coaching remain documented later features, not simulated working integrations.

Agent inputs are validated plain dictionaries. Record schemas: climbs `{id, terrain: slab|vertical|overhang, movement: controlled|dynamic, completed: bool, attempts: int, grade, grade_system, location, occurred_at}`; assessments `{id, metric, value, unit, method: manual|camera, protocol, confidence, occurred_at}`; hands `{id, side: left|right, region, pain: 0..10, note, occurred_at}`; activities `{id, kind, duration_minutes, source: manual, occurred_at}`. Agents may return additional explained fields; parent integrates and verifies HTTP output.

## TDD execution example

Run from `backend/`:

```python
def test_identity_can_be_read_with_issued_token(client):
    created = client.post('/v1/climbers', json={'name': 'Monkey', 'goal': 'technique'})
    assert created.status_code == 201
    token = created.json()['token']
    response = client.get('/v1/me', headers={'Authorization': f'Bearer {token}'})
    assert response.status_code == 200
    assert response.json()['name'] == 'Monkey'
```

First run: `.venv/bin/python -m pytest tests/test_api.py::test_identity_can_be_read_with_issued_token -q` must show missing endpoint (404). Implement the endpoint and persistence then rerun the focused and current full suite. Apply this same small loop to each pending scenario, not a batch of tests followed by a batch of code.
